## local embedding models  (utils/embedding.py -> LOCAL_MODELS)

WHY
OpenAI embeddings cost money, send your documents to OpenAI, and need internet.
Local models (Hugging Face, via sentence-transformers) download once, then run free, private and offline.

MODELS ADDED
  all-MiniLM-L6-v2          384 dims, reads 256 tokens   tiny + fastest, baseline
  BAAI/bge-small-en-v1.5    384 dims, reads 512 tokens   same size as MiniLM, better on benchmarks (MTEB)
  BAAI/bge-base-en-v1.5     768 dims, reads 512 tokens   best quality of the list, slower
  intfloat/e5-base-v2       768 dims, reads 512 tokens   needs prefixes on BOTH question and chunks
  all-mpnet-base-v2         768 dims, reads 384 tokens   older all-rounder

GOTCHA 1: PREFIXES
BGE and E5 were trained with an instruction in front of the text:
  BGE question : "Represent this sentence for searching relevant passages: "
  E5           : "query: " for questions, "passage: " for chunks
Without it, results silently get worse. That's why there are 2 methods now:
  embed(texts)       -> chunks    (adds the passage prefix, if any)
  embed_query(text)  -> question  (adds the query prefix, if any)   <- the Retriever uses this
Demo result (BGE small): gap between right and wrong answer 0.058 without prefix -> 0.082 with prefix (~40% bigger).

GOTCHA 2: LENGTH LIMIT
Every model reads at most N tokens (~4 characters each) and SILENTLY IGNORES THE REST.
Demo: page 35 = 448 tokens -> MiniLM reads only 57% of it, BGE reads 100%.
A fact at the bottom of a long page-wise chunk is invisible to MiniLM.
Rule: MiniLM -> small chunks (recursive, size <= 800 chars). BGE/E5 -> page-wise is safer.

GOTCHA 3: SCORES CAN'T BE COMPARED BETWEEN MODELS
Same question, same page 35:  BGE score 0.84, MiniLM score 0.67.
BGE squeezes everything into a high range (even an unrelated sentence got 0.43), MiniLM spreads out.
Only compare the ORDER within one model, or the gap between #1 and #2.

RESULT IN THE APP  (page-wise, question "How much annual revenue is needed to fund new data centers by 2030?")
  BGE small : p.35 first (vector 0.84) -> correct answer "$2 trillion"
  MiniLM    : p.35 first (vector 0.67) -> correct answer "$2 trillion"
  Both worked. MiniLM was lucky: the fact is at the TOP of page 35, inside the 57% it reads.

LESSON: ALWAYS CHECK THAT RESULTS MAKE SENSE
First MiniLM screenshot showed EXACTLY the same vector scores as BGE (0.84 / 0.67 / 0.63).
Two different models can't give identical scores -> it was a bug: the app did not clear the chat
after a rebuild, so the OLD BGE answer was still on screen. Fixed in frontend/app.js (clearChat() after build).
After a refresh (Ctrl+F5) the real MiniLM score for p.35 was 0.67.

OTHER NOTES
- loaded models are kept in memory (_loaded_models), so a 2nd pipeline doesn't reload them
- vectors are normalized (length 1) -> cosine similarity = simple dot product
- each pipeline gets its own Chroma collection, so 384-dim and 768-dim vectors never mix

TRY IT
  python -m evals.embedding_demo     -> parts 1-3 above (question vs sentences, prefix, length limit)

HOW TO IDENTIFY A GOOD EMBEDDING MODEL
Step 1 - shortlist (check the basics):
  - MTEB leaderboard (Hugging Face): look at the RETRIEVAL column, not the overall average
  - max tokens >= your chunk size (else text is cut off, like MiniLM on page 35)
  - size / speed: start small (BGE small), only go bigger if it's not good enough
  - dims: 384 vs 768 vs 1536 -> bigger = more storage, slower search
  - language: English-only models fail on Hindi/mixed text -> use multilingual (BGE-m3, multilingual-E5)
  - prefixes: does it need "query: " etc.? Forgetting = silently worse
  - license + privacy: local or API? commercial use allowed?
Step 2 - decide (test on YOUR documents, benchmarks use other people's data):
  1. write 10-20 questions about your PDF + note the page that holds each answer
  2. run every candidate model on the SAME chunks
  3. measure  Hit@3 = how often the right page is in the top 3
              MRR   = how high the right page ranks on average (1.0 = always #1)
  4. pick the smallest/cheapest model that scores well enough
Tip: use HARD questions (different words than the document, details deep inside a long page,
facts only in a chart). Easy questions -> every model scores 100% -> nothing to compare.


## collection
A design point to keep in mind: the two embedders produce vectors of different sizes (384 for MiniLM, 1536 for OpenAI).
A single collection can only hold one size, and vectors from different models can't be compared anyway. 
So we'll create one collection per embedding model, for example bain_minilm and bain_openai.

## image parsing  (utils/image_parsing.py)

PROBLEM
pypdf only reads TEXT. Charts, tables-as-pictures, diagrams and scanned pages are invisible or scrambled.
Example, page 34 (the compute chart), as pypdf sees it:
  - Y-axis 10^25, 10^23 ... came out as "1025, 1023" -> superscripts flattened, numbers wrong
  - model labels (GPT-4, Gemini Ultra) present, but not WHICH value belongs to which model
  - "efficiency" came out as "e/f_f.shorticiency" (the "ffi" ligature got garbled)
  - "4.5x every year" chopped into 4 separate lines
So a question about the chart had no good chunk to retrieve.

IDEA
Look at the page the way a human does: render it to an image and ask a vision LLM to describe it.

STEPS
1. classify_page()  -> which pages have visual content? (PyMuPDF, free, no API)
     big image      : an image covering >= 5% of the page    (MIN_IMAGE_SHARE)     -> skips small logos
     vector chart   : >= 30 drawn lines/shapes               (MIN_VECTOR_DRAWINGS) -> charts drawn as vectors, not images
     scanned page   : almost no text (<= 20 chars) but has content (SCANNED_MAX_CHARS)
   Bain report: 39 of 77 pages flagged.
2. render each flagged page to a PNG (RENDER_DPI = 150) and send it + a prompt to the OpenAI vision model
     FIGURE_PROMPT : describe charts/tables with all numbers, labels, axes; ignore logos/photos; reply NONE if nothing useful
     SCAN_PROMPT   : scanned page -> transcribe all the text
3. each description becomes a Chunk:  text = "[Visual content on page 34] ...",  metadata type = "figure"
     - figure chunks are NEVER split (half a table is useless)
     - scanned-page text joins the normal pages and goes through normal chunking
     - "NONE" answers are dropped

WHY RENDER THE WHOLE PAGE, NOT EXTRACT THE IMAGES?
Many charts are VECTOR graphics, not image files. Page 34 has 402 drawing commands and 0 images ->
image extraction would have missed it completely. A rendered page also includes the figure title and axis labels.

THRESHOLD TRADE-OFF
Loose thresholds (current) = nothing missed, but some wasted calls on decorative pages.
Strict thresholds          = cheaper, but small charts can be missed.
Chose loose: a missed chart is worse than a few cents. Decorative pages cost a call but are not stored (NONE).

COST + SPEED
- one vision call per flagged page, 6 calls run in parallel (ThreadPoolExecutor)
- results cached in cache/vision/<pdf fingerprint>_<model>.json -> same PDF again = free + instant
- a failed page is not cached, so it is retried on the next build
- off by default: "Images" switch in the app / images.enabled in the config

WHAT I SAW (gpt-5.6-luna)
- page 34 (vector chart): full description, Y-axis read correctly as 10^15..10^25, both trend lines + "4.5x every year"
  vs "2x every two years (Moore's law)", title, notes and source.
  Weakness: lists the model names but NOT their approximate values -> could add a prompt line for that.
- page 11 (decorative "At a Glance" photo): answered NONE -> correctly skipped.
- In the app, question "How fast is AI compute demand growing compared to chip efficiency?":
  source #1 was "p. 34 . figure" with rerank score 0.96, higher than page 34's own text (0.92).

TRY IT
  python -m utils.image_parsing              -> list flagged pages (free)
  python -m utils.image_parsing --page 34    -> one page, saves cache/page_34.png, prints description
  python -m utils.image_parsing --describe   -> all flagged pages

OTHER WAYS (not used here)
- OCR (Tesseract, EasyOCR): free + local, reads text in images but does NOT understand charts
- local vision models (e.g. Qwen2-VL, Florence-2 via Hugging Face): free, but slow without a GPU
- layout parsers (Docling, Unstructured, LlamaParse): detect tables/figures as separate elements

## chunking  (utils/chunking.py)

WHY IT MATTERS
The LLM only sees the chunks retrieval finds. Badly cut chunks (mid-sentence, two topics mixed,
answer split in half) -> worse retrieval -> worse answer.

THE 4 STRATEGIES
  page-wise  : 1 chunk per page. Simple, good citations. Chunks are long (avg ~1800 chars) and mix topics.
  character  : cut every N chars, repeat `overlap` chars. Cuts mid-word ("(Amazo" / "ng: lots of").
  recursive  : try to cut at paragraph -> line -> sentence -> word -> character, then glue pieces up to N chars.
               Clean borders ("...their businesses." / "Will AI change that?").
               Overlap = whole pieces only -> with overlap 50 there was NO real overlap (lines > 50 chars), see fix 5.
  semantic   : split into sentences, embed each (with its neighbours), cut where the meaning jumps most.
               breakpoint_percentile 90 = cut at the 10% biggest jumps (lower = more, smaller chunks).
               Never across pages; max size comes from the embedding model (fix 3).

HOW WE TESTED  (evals/)
  python -m evals.chunking_demo       -> see how each strategy cuts (borders, sizes, token fit)
  python -m evals.chunking_retrieval  -> 3 questions, top 3 chunks per strategy (first quick look)
  python -m evals.chunking_eval       -> THE full test: 9 setups x 2 embedders x 22 questions
    - answer key = answer phrase; the script finds EVERY page containing it (reports repeat facts)
    - question kinds: top / middle / END of a long page (7) / chart (3) / paraphrase (4)
    - Hit@k = answer inside a top-k chunk, MRR = how high, end@3 = only end-of-page questions,
      ctx = characters in the top 3 chunks (what the LLM must read)

WHAT WE LEARNED
1. The embedding model matters as much as chunking: BGE ~80% avg Hit@3 vs MiniLM ~73%.
   Paraphrase "How quickly did the price of o3 fall?" (report: "dropped 80%"): MiniLM missed it in 6/8 setups, BGE #1 in all 8.
2. Page-wise is NOT bad with BGE (best Hit@3 91%): the page is found by its beginning, and the LLM then gets
   the WHOLE page, end included. With MiniLM (reads ~1000 chars) page-wise was the worst (64%, end@3 29%).
   Price: ctx 6369 = the LLM reads ~5x more text than with character 500 -> more cost, slower, more noise.
   (Correction: earlier I said page-wise "can't see" the end of long pages - true for the vector, not for the answer.)
3. Overlap matters: recursive with fake overlap (50) was worse than character; overlap 150 fixed most of it (fix 5).
4. With a reranker, Hit@5 matters more than Hit@1: the reranker reorders, it just needs the answer in the candidates.
   Semantic 80 + BGE had the best Hit@5 (95%) at less than half the context of page-wise.
5. Testing lesson: my first answer key was wrong (pricing is also on p.32, "22%" also on p.17).
   Always let the script find ALL pages with the answer, and use HARD questions.

APP CHECK  (BGE small + semantic 80 + Cohere rerank, the 2 questions almost every setup missed)
  "How much old or inaccurate content may need to be removed before using AI?"
      -> "as much as 80%", p.63 #1, rerank 0.68 (next best 0.09)                          CORRECT
  "What is still holding back humanoid robots in handling objects?"
      -> "dexterity and fine-motor control ... tactile sensitivity and precision", p.38   CORRECT
      vector order had p.37 (0.72) above p.38 (0.70); the reranker moved p.38 to #1 (0.80 vs 0.58)

RECOMMENDATION
  Best for the app (with reranker) : BGE small + semantic 80
  Cheapest / smallest context      : BGE small + character 500 (or recursive 500 with overlap 150)
  Avoid                            : MiniLM + page-wise, recursive 800, recursive with tiny overlap

FIXES
Fix 1 - dot leaders made 5-character chunks  (split_sentences)
  Problem : semantic chunking splits text into sentences at every ". " (dot + space).
            The table of contents has "dot leaders":  "Quantum Computing . . . . . . 41"
            -> every ". " looked like a sentence end -> useless chunks like ". .68" (5 chars)
  Fix     : before splitting, replace 3 or more dots with one "…" (not a normal dot, so no split there)
              text = re.sub(r"(?:\.\s?){3,}", "… ", text)
  Example : "Quantum Computing . . . . . . 41"  ->  "Quantum Computing … 41"  (stays one piece)

Fix 2 - tiny leftover chunks  (semantic_chunking -> close_chunk)
  Problem : a chunk is closed when (1) the topic changes, (2) it gets too long (>1500), (3) a new page starts.
            min_chunk_size (200) was only checked for (1). So after a "too long" cut, a short leftover
            like "See Figure 3." became its own chunk -> no meaning, wastes a top-3 slot.
  Fix     : when closing a chunk shorter than 200 chars, glue it onto the PREVIOUS chunk if it's on the SAME page
              if len(text) < min_chunk_size and chunks and chunks[-1].metadata["page"] == page:
                  chunks[-1].text += " " + text
                  return
  Example : chunk A (1450 chars) + chunk B "See Figure 3." (13 chars)  ->  chunk A (1464 chars)
  Limits  : - never glued across pages (citation page would be wrong) -> cover page (59) and last page (40) stay small
            - a merged chunk can go up to ~199 chars over the 1500 max (better than a useless tiny chunk)

Result of fix 1 + 2  (python -m evals.chunking_demo, semantic, percentile 90, MiniLM)
            before   after
  min          5      40     <- tiny chunks gone; 40 = last page "visit www.bain.com" (a whole page, can't merge)
  chunks     162     144     <- 18 tiny pieces glued onto their neighbours
  avg        831     927
  max       1498    1598     <- expected: merging can go up to 199 over the 1500 max

Fix 3 - semantic chunks were bigger than MiniLM can read  (semantic_max_chunk_size)
  Problem : max chunk size was a fixed 1500 chars (1598 after fix 2), but MiniLM reads only
            256 tokens (~1000 chars) -> the end of every long chunk was invisible to search.
  Fix     : let the embedding model decide (option C; A = lower it for everyone, B = a setting in the app)
            - every embedder now has  max_tokens  (MiniLM 256, BGE 512, OpenAI 8191)
            - max chunk size = smaller of (1500, max_tokens x 4 chars - 200 margin for fix-2 merges)
  Example : MiniLM : 256 x 4 = 1024 - 200 = 824 chars
            BGE    : 512 x 4 = 2048 - 200 = 1848 -> capped at 1500 (bigger chunks mix too many topics)
            OpenAI : capped at 1500
  Check   : "4 chars per token" is only an estimate -> Part 5 of the demo counts the REAL tokens
  Result  : (percentile 90, MiniLM)  chunks 144 -> 218, avg 927 -> 612, max 1598 -> 1410
            216 of 218 chunks now fit completely. 2 chunks are still cut off (p18: 285 tokens, p53: 343 tokens).
  Known issue (left as is for now):
            both are CHART text with no full stops ("7K 6K 0 1K 2K 3K 4,460 18% 2020 ...") -> the sentence
            splitter sees one 1000+ char "sentence", and semantic chunking only cuts BETWEEN sentences.
            Also number-heavy text is ~3.6 chars/token, so "4 chars per token" is too optimistic there.
            Possible fix 4: cut over-long sentences with recursive chunking + use 3 chars/token.

Fix 5 - recursive chunking had almost no overlap  (frontend/index.html, default overlap 50 -> 150)
  Problem : recursive only repeats WHOLE pieces (lines) as overlap. Lines in this PDF are longer than 50 chars,
            so with overlap 50 nothing fits -> in practice NO overlap -> a fact at a chunk border gets split.
            Character chunking always repeats 50 chars, so it doesn't have this problem.
  Test    : python -m evals.chunking_eval --setups "recursive 500" "recursive 500/150" "character 500"
                                          --embedders BAAI/bge-small-en-v1.5
                              Hit@1  Hit@3  Hit@5   MRR  end@3  chunks
            recursive 500      64%    73%    82%   0.69   57%    337
            recursive 500/150  73%    77%    82%   0.76   71%    406
            character 500      64%    82%    82%   0.71   86%    332
  Result  : overlap helps: end-of-page 57% -> 71%, best Hit@1 and MRR of the three.
            Hit@3 still 1 question below character (= noise level with 22 questions).
            Cost: ~20% more chunks (repeated text).
  Fix     : default overlap in the app is now 150. (Also applies to character chunking - not tested there.)

Is this the right way?
  Yes for the method: measure (min = 5) -> look at the actual bad chunks -> fix the real cause.
  Fix 2 is standard (LangChain's SemanticChunker also has a minimum size).
  But fix 1 is a patch for this PDF. Two weaknesses remain:
    - our sentence splitter is basic: it also splits wrongly on "e.g. " or "U.S. "
      -> proper splitters know abbreviations: nltk, spaCy, pysbd
    - no CLEANING step: every chunk starts with "33 Technology Report 2025" (page number + header),
      and the table of contents gets indexed -> noise in EVERY strategy
  More robust order:  PDF -> clean text (headers/footers/TOC) -> good sentence splitter -> chunking

## document parsing  (industry standard, works for ANY pdf)

WHY
pypdf only gives raw text per page. Seen on our 2 PDFs:
  - Bain: page number + "Technology Report 2025" glued to the start of ~70 of 77 chunks, table of contents indexed
  - Atomic Habits: 69,238 tabs between words, small caps split ("P" + "ENGUIN"), 60 words broken across lines
Hand-written cleaning rules only fit THESE two files. Users upload anything (charts, tables, scans, books).
Industry standard: a LAYOUT-AWARE parser understands each page first (headers/footers, headings, paragraphs,
tables, figures, reading order, OCR for scans), THEN chunking works on clean, structured text.
Chosen: Docling (IBM, open-source, local, free). Downside: slow on CPU the first time -> results get cached.

PLAN (one step at a time):  0 setup | 1 clean reading (Docling) | 2 proper sentence splitter (nltk)
  | 3 sizes in tokens | 4 cut over-long "sentences" | 5 chunks may continue onto the next page
  | 6 new strategy: chunk by section (Docling HybridChunker)

STEP 0 - setup (done)
  - .gitignore: assets/Atomic Habits*.pdf  (copyrighted book: use locally, never push to GitHub)
  - first a DRY RUN (pip install --dry-run docling nltk) = "show what you would install, change nothing"
    -> checked that torch 2.15.0 is NOT replaced
  - pip install docling nltk -> ~50 new packages, 2 downgrades:
        huggingface_hub 2.4.0 -> 1.33.0  (Docling needs < 2; sentence-transformers accepts 1.3 - 3)
        typer 0.29.1 -> 0.27.3           (command-line helper, not used by our code)
  - requirements.txt: docling==2.151.1, nltk==3.10.4
